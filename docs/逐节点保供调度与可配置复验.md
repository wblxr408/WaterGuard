# 逐节点保供调度与可配置复验

目标是故障发生后由 AGH 选择具体设施和动作时刻，交给水力引擎实际执行；独立验证器从原始结果计算每个用水节点的保供改善，按原始冻结约束和用户指定的需求增幅 x 复验同一方案。

## 正常供水时间的定义

一个节点在一个原始水力区间内，压力满足冻结最低压力、实际交付需求与期望需求之比满足冻结最低供需比，才计入正常供水时长。零需求节点的供需比不适用，仍检查压力。压力和供需比同时失败只扣一次时长。

节点正常供水时间占比 = 满足两项约束的区间时长之和 / 该节点全部评估区间时长。计算使用原始内部水力区间，包括控制事件之间的区间；按秒积分，不能按展示帧数量计数。评价对象是原模型的全部用户节点；仿真生成的泄漏位置节点不属于新增用户。

报告的 `node_availability` 保留每个节点的评估秒数、正常供水秒数和占比；`min_node_time_pass_ratio` 是最差节点占比，`mean_node_time_pass_ratio` 是各节点等权平均，不能用全网按需求量加权的供需比代替。

当前启用应急层的新任务按民生顺序冻结：声明的关键用水点全程应急覆盖（若有）、全网全程应急节点数、应急平均达标时长，再比较正常层最差与平均、缺水和动作成本。未启用应急层时沿用最差节点正常供水时间、平均节点时长、缺水与成本的顺序；历史任务保持原有冻结目标。主机按任务中的 `objectives` 比较实际报告，不允许模型填写指标。所有节点达到100%时，相应覆盖指标达到上限；预算内比较只能说明已测方案的优劣。实测三策略与零增益归因见[最新验收](submission/民生优先与混合策略验收.md)。

## 原始约束与推荐

正常供水时间是优化指标，原始压力和供需比仍逐节点、逐区间检查。存在违规的方案即使比基线好，也不能获得完全达标推荐。父运行返回 `best_effort_candidate_id` 供比较；有效方案优于同任务无动作基线并满足改善及原生证据条件时，正式交付 `BEST_EFFORT_MITIGATION`，以 `mitigation_candidate_id` 指向挽救方案；`selected_candidate_id` 仅指完全达标推荐。当前工作区另以 `dispatch_recommendation` 推荐原生有效的最佳已验证应急处置，明确标注尽力挽救或最佳保底、完整准入与违规，不回写历史字段。逐节点回退与未完成复验均保留。缺少基线或有效关联时不推断挽救成功。

完全达标推荐需要名义约束通过、同 `plan_hash` 的实际需求复验通过、原生 AGH 调用关联和完整证据。仿真计算完成、模型宣称成功或者只有总缺水下降，均不满足这个条件；应急处置推荐单独呈现已验证效果和未达标范围。

## 参数入口

运行默认值集中在 `config/dispatch-defaults.json`。可用 `WG_DISPATCH_CONFIG` 指向另一份部署配置；有效值进入冻结 TaskSpec 和任务哈希，修改配置不影响已有任务。配置涵盖需求增幅、参考基线保留比例、时间窗口、故障参数、压力与供需比阈值、水力设置、模型参数、操作时限、预算和目标顺序。

任务界面可输入任意正数需求增幅 x，包括小数。`POST /api/tasks/from-proposal` 支持 `demand_increase_pct`、`fault_parameters`、`time_window`、`hydraulic_options`、`physical_parameters`、`action_limits` 和对原生控制的准确 `control_overrides`。完整 TaskSpec 可通过现有任务 API 提交，设施 ID 来自实际模型与动作目录。

需求复验倍率 = 名义倍率 × (1 + x / 100)。例如名义倍率 1.2、x=23.75 时，复验倍率为 1.485，不能仍用 1.1，也不能把名义倍率当作复验。标签、参数、任务和计划绑定由编译器检查；改标签不能绕过实际计算。

改变物理模型或时间窗口时，手动提交对应的冻结验收阈值；默认自适应参考来自既定无故障模型，不能拿它替代另一组输入的标定。算法支持的物理语义、数值完整性规则和资源边界属于可验证的实现条件。历史 fixture、公开研究场景和测试用例中的固定输入用于复现，不用于决定线上故障的答案。

## 100% 的含义与实时响应缺口

2026-10-12 用户质疑故障后的 100% 结果。核查显示评估窗口为仿真 3600–10800 秒，包含故障发生到计划动作的前 300 秒，以及 7200 秒故障结束后的恢复时段。正常指满足冻结的 20 m / 95% 标准，不代表保持故障前压力。节点 23 在故障前 3300 秒压力约 85.773 m，故障发生时降到 20.764 m，仍达标。无动作时从 6300 秒起低于 20 m，直到 7200 秒故障结束，共 900 秒不达标；供需比一直高于 95%。计划在 3900 秒关闭管段 11 后，这些区间压力保持达标，因此离线计划为 7200/7200 秒。已经发生的不达标时长不能通过后续恢复抹除。

上述 3900 秒是离线计划的假定时刻（故障起 +300 秒），而当时真实原生会话从 02:59:54.512Z 到最终提交 03:09:24.144Z 实际耗时 569.632 秒。把动作钉在 3900 秒属于回填：决策物理上要到约 570 秒后才就绪。这一缺口已经按下节的实时验收机制修复。

## 实时动态决策与无回填强制（2026-10-12 实现）

实时验收不再允许任何假定响应时刻。动作最早生效时刻由真实延迟推导并由服务端强制：

```
earliest_effective_s = fault_start + ceil((detection_s + decision_wall_clock_s + actuation_s) / step_s) * step_s
```

- `detection_s`、`actuation_s` 为冻结工程假设，默认检测 60 秒、执行 120 秒，集中在 `config/dispatch-defaults.json` 的 `response_latency`。
- `decision_wall_clock_s` 为真实 AGH 决策墙钟：从原生事件日志 `agh/native/events.jsonl` 的 `session/start` 时间戳到选定方案 `wg_submit_plan` 调用时间戳，可被审计独立重算；监控用的单调 `wall_time_s` 不能替代它，因为后者还含宿主打包时间。
- 时间按秒 1:1 映射到仿真秒，向上取整到控制边界步长。对确定性引擎，从 t=0 重跑并在该时刻注入动作，与在线单状态持续推进物理等价；唯一不诚实的是回填的动作时刻，不是重跑本身。

强制点与无回填保证：

- `TaskSpec` 新增可选 `response_latency{detection_s, actuation_s, decision_wall_clock_s, earliest_effective_s, measurement, source}`，纳入 `constraint_hash`，事后不能悄悄调低。
- `check_task`（契约层）在存在 `response_latency` 且有故障时，强制 `evaluation_start_s == fault.start_s`（从故障起累计全部不达标时长），并强制 `action_limits.earliest_s >= earliest_effective_s`。
- `check_plan` 现有的逐动作 `earliest_s <= simulation_time_s` 门即无回填门：任何早于真实延迟地板的动作在编译期被拒绝，模型无法绕过提交路径回填。
- 验收脚本独立从冻结原生日志重算决策墙钟，断言冻结地板不低于据此推出的地板，否则判定回填并失败。

累计不达标时长、逐节点改善与同方案 x 复验：评估窗从 `fault.start_s` 起，验证器的 `node_availability` 已逐节点按秒积分，故障后到动作生效前的全部不达标秒数都计入；逐节点正常供水秒数对无动作基线逐一比较，要求无节点回退且至少一处改善；同 `plan_hash` 在倍率 `名义 × (1 + x/100)` 下复验。改善但仍违规或复验失败，可以正式交付 `BEST_EFFORT_MITIGATION`，仍不得推荐。`NO_FEASIBLE_FOUND` 表示本次搜索没有取得完整准入或可证明的挽救改善，不是物理无解证明。

验证入口：

```powershell
# 确定性实时证明（离线，用声明/实测决策墙钟；覆盖多故障场景）
.venv/Scripts/python.exe experiments/realtime_dispatch.py --output artifacts/realtime-dispatch
# 模型自主决策的实时 Live 验收（启动 AGH/API/前端并配置模型后）
.venv/Scripts/python.exe experiments/dispatch_acceptance.py --proposal experiments/dispatch-success-proposal.json --output artifacts/realtime-live
```

`experiments/realtime_dispatch.py` 对每个冻结故障场景推进故障后时间线、把最优许可动作钉在强制地板、从故障起累计不达标、逐节点对比无动作基线并做 x 复验，诚实负结果照样保留。`experiments/dispatch_acceptance.py` 则要求真实 AGH 在同一会话内自主选择动作，并用实测决策墙钟独立复核无回填。

### 已验证的 Net1 真实延迟结果

对已验证的 Net1 管段 22 泄漏（面积 0.01865 m²、x=7.5%），实测决策墙钟 569.632 秒加检测 60、执行 120 秒，强制最早动作时刻由回填的 3900 秒提高到 **4500 秒**（故障起 +900 秒，向上取整到步长）。确定性复算显示：无动作基线节点 23 仅 6300/7200 秒达标、缺供 0.018608 m³、最低压力 19.831 m；在诚实的 4500 秒关闭管段 11 后，9 个用水节点全部 7200/7200 秒达标、缺供归零、最低压力 20.581 m，x=7.5% 同方案复验通过。因不达标区间（6300–7200 秒）出现在 4500 秒动作之后，诚实延迟下该案例仍恢复 100%——这是实算结果，并非预先断言；更严重的故障、破管或中国管网断裂场景按真实延迟会保留诚实负结果。

## 正式尽力挽救交付（2026-10-12）

确定性候选轮流覆盖单动作、恢复时序以及 2 至冻结动作上限的多设施组合；默认新任务为 16 次仿真预算、4 个动作。故障设施和隔离边界仍不可操作，原生受控备用泵必须有显式授权。排序统一使用任务 `objectives`，不再使用配置外加权评分。

独立报告提供 `fully_compliant_node_count`、`assessed_node_count`、逐节点时长及平均/最差达标率。`recommendation-summary.json` 的 `mitigation` 保存基线和挽救逐节点差值、回退、残余违规数量及复验状态，工作台展示相同数据。降级服务为独立附加层。用户已确认 15m/75%，兼容的新任务默认冻结该值并独立展示覆盖率；显式 null 可停用。自定义或自适应完整门槛低于它时不自动添加更严格的降级层。历史冻结任务保持原有配置。

实验入口：`.venv\Scripts\python.exe experiments/realtime_dispatch.py --only net1-leak-22 net3-closure-123 --output artifacts/mitigation-v1`。实验使用 24 次预算、4 个动作，保留基线和同方案复验的预算，动作不早于 4500s。实验默认使用已确认的 15m/75%；显式的 `--emergency-pressure-m` 和 `--emergency-supply-ratio` 可覆盖实验参数并记录到新任务。此为确定性物理实验，工程达标也不授予 AGH 推荐资格。
